# 영양 분석 계산 과정과 알고리즘

## 파일 구성과 JSON 계약

영양 계산 구현은 nutrition 폴더 안의 다음 세 파일을 중심으로 구성한다.

| 파일 | 역할 |
|---|---|
| __init__.py | 기존 analyze_meal 공개 함수 연결 유지 |
| engine.py | 기준표, EER, 섭취량 환산, 판정, 추천을 모두 구현 |
| Algorithm.md | 계산 과정, 출처, JSON 예시, 검증 및 데이터 연결 설명 |

추가 계산 모듈을 설치하지 않고 기존 API 스키마, 라우터와 DB 모델을 사용한다.
요청 JSON과 응답 중첩 구조, camelCase 필드명과 자료형을 유지한다.
사용자가 허용한 nutrients.carbohydrate와 nutrients.vitaminD만 기존 영양소와 같은 구조로 추가한다.
기존 철분과 나트륨 키와 실제 섭취량은 유지하지만 이번 기준 적용 범위 밖이므로 target/ratio/upperLimit은 null, status는 UNKNOWN이다.
추가 설명은 기존 warnings 필드에 넣는다. explanation 같은 새 응답 필드는 만들지 않는다.

## 1. 적용 범위와 출처

만 6-18세의 입력 프로필과 기록된 한 끼를 대상으로 한 **식사계획 비교 도구**다.
실제 영양상태 진단, 질환별 처방, 체중감량 목표 산출을 하지 않는다.
입력 JSON은 공모전 설명 PDF의 영문 키와 기존 API 모델을 유지한다.

**기준 수치 출처:** 사용자가 제공한 `2025_한국인영양소섭취기준_활용 1.pdf`.
아래 PDF 쪽수는 188쪽 파일에서 1부터 센 위치다. 뒤쪽의 2020 부록 표와 혼합하지 않았다.

| 자료 위치 | 사용 내용 |
|---|---|
| PDF 11쪽 / xi | 탄수화물 에너지적정비율 50-65%, 단백질 10-20% |
| PDF 12쪽 / xii | 탄수화물 권장섭취량 130g/일, 평균필요량 100g/일 |
| PDF 13쪽 / xiii | 단백질의 연령과 성별 권장섭취량과 평균필요량 |
| PDF 15쪽 / xv | 비타민 A 권장섭취량, 비타민 D 충분섭취량, 상한섭취량 |
| PDF 16쪽 / xvi | 비타민 C 권장섭취량과 상한섭취량 |
| PDF 19쪽 / xix | 칼슘 권장섭취량과 상한섭취량 |
| PDF 39-40쪽 / xxxix-xl | 개인 섭취평가와 식사계획에 각 기준을 적용하는 원칙 |
| PDF 46쪽 / 본문 2쪽 | EER 산출과 저활동적 수준의 기본 적용 설명 |

**에너지 공식과 활동계수:** 곽지연 외, 「한국 소아청소년을 위한 신체활동분류표의 타당도 평가 및 이를 이용한 일일 총에너지소비량, 에너지필요추정량과 신체활동 평가」, J Nutr Health. 2023;56(1):35-53.
[논문 원문](https://www.e-jnh.org/pdf/10.4163/jnh.2023.56.1.35), DOI 10.4163/jnh.2023.56.1.35.
제공 논문 PDF 5쪽(본문 39쪽)의 공식과 PDF 10쪽(본문 44쪽) Table 5 주석의 PA 계수를 사용했다.
논문에서 사용한 공식의 근원은 2020 KDRI이며, 논문 자체가 새로운 개인별 공식을 개발한 것은 아니다.
Table 5 주석의 연령 표기에 9-19가 있으나, 본문 공식, 연구대상과 기존 API에 따라 9-18세까지만 지원한다.

이 연구의 2부 대상자는 6-18세 166명이며, EER이 비교 에너지소비량을 정확히 예측한 비율은 29.6%, 과대추정 비율은 47.3%였다.
따라서 공식을 사용했다는 이유만으로 개인의 정확한 필요량이나 이 앱의 효과가 검증됐다고 설명하지 않는다.

**비타민 A 해석 보조 확인:** [NIH ODS Vitamin A and Carotenoids](https://ods.od.nih.gov/factsheets/VitaminA-HealthProfessional/).
총 RAE와 레티놀형 비타민 A를 구별해야 하므로, 형태가 없는 DB 값으로 상한 초과를 단정하지 않는다.
미국의 연령별 기준 수치는 사용하지 않았다.

## 2. 전체 처리 순서

1. 기존 FastAPI/Pydantic이 JSON을 검증한다.
2. foodId로 DB 상품을 조회한다. 미등록 상품이면 기존 라우터에서 404를 반환한다.
3. 성별과 연령군으로 2025 기준표의 행을 선택한다.
4. 키를 cm에서 m로 바꾸고 EER을 계산한다.
5. 하루 기준을 mealsPerDay로 나누어 한 끼 계획량을 구한다.
6. 입력 수량을 DB의 1회 제공량 기준으로 환산한다.
7. 영양소마다 단위와 품질을 확인하고 전체 상품의 섭취량을 합산한다.
8. 누락 여부, 기준의 종류(RNI/AI/AMDR), 하루 상한을 고려해 상태를 구한다.
9. 조건을 만족하는 보완 식품을 점수순으로 정렬한다.
10. 기존 응답 모델로 camelCase JSON을 반환한다. DB는 변경하지 않는다.

## 3. EER 계산

변수: A=만 나이(년), W=체중(kg), H=키(m), PA=신체활동단계별 계수, G=성장에너지(kcal/일).

```text
남아 = 88.5 - 61.9*A + PA*(26.7*W + 903*H) + G
여아 = 135.3 - 30.8*A + PA*(10.0*W + 934*H) + G
G = 20 (6-8세), 25 (9-18세)
H = heightCm / 100
```

| 활동단계 | 남아 PA | 여아 PA |
|---|---:|---:|
| 비활동적 | 1.00 | 1.00 |
| 저활동적 | 1.13 | 1.16 |
| 활동적 | 1.26 | 1.31 |
| 매우 활동적 | 1.42 | 1.56 |

기존 입력에는 활동량이 없으므로 **저활동적을 공통 기본값으로 가정**한다.
2025 자료의 기본 적용 방식을 참고한 선택이며, 개인의 활동량을 알아낸 결과는 아니다.
기존 warnings에 ACTIVITY_ASSUMED와 실제 수치 대입식을 제공한다.
calculate_eer 함수는 내부 연구와 비교용으로 다른 활동단계를 인자로 받을 수 있지만 공개 API 입력에 새 필드를 추가하지 않았다.
개별 공식의 소수점 결과를 유지하며 요약표의 대표 체위 기준 EER이나 100kcal 절삭값으로 바꾸지 않는다.

## 4. 연령과 성별 하루 목표표

단백질, 칼슘, 비타민 A와 C는 **권장섭취량(RNI)**, 비타민 D는 **충분섭취량(AI)**이다.

| 성별 | 만 나이 | 단백질 g | 칼슘 mg | 비타민 A µg RAE | 비타민 C mg | 비타민 D µg |
|---|---|---:|---:|---:|---:|---:|
| 남 | 6-8 | 35 | 700 | 450 | 50 | 5 |
| 남 | 9-11 | 50 | 800 | 600 | 70 | 5 |
| 남 | 12-14 | 60 | 950 | 750 | 90 | 10 |
| 남 | 15-18 | 65 | 800 | 850 | 100 | 10 |
| 여 | 6-8 | 35 | 700 | 400 | 50 | 5 |
| 여 | 9-11 | 45 | 800 | 550 | 70 | 5 |
| 여 | 12-14 | 55 | 850 | 650 | 90 | 10 |
| 여 | 15-18 | 55 | 700 | 650 | 100 | 10 |

한 끼 목표 = 하루 목표 / mealsPerDay. 이는 공인된 한 끼 영양섭취기준이 아니라 서비스의 균등 배분 정책이다.
BREAKFAST/LUNCH/DINNER/SNACK 구분은 반환하지만 별도 식사비중 입력이 없어 모두 동일 분모를 쓴다.
간식이나 끼니 수를 실제와 다르게 입력하면 비교 목표도 달라진다.

탄수화물은 EER과 연결한 식사계획 범위를 사용한다.

```text
하루 계획범위(g) = [EER * 0.50 / 4, EER * 0.65 / 4]
target = 범위 중간값 / mealsPerDay = EER * 0.575 / 4 / mealsPerDay
```

50-65%는 자료의 기준이고, 단일 target에 중간값을 넣는 것은 JSON 계약을 유지하기 위한 서비스 선택이다.
이 값은 130g/일 RNI와 다르다. 130g/일과 평균필요량을 내부 기준 자료에 별도로 보존한다.
계산된 중간값이 130g/일보다 작은 예외에서는 입력 체위 검토 경고를 반환하고 탄수화물 상태와 자동 추천을 보류한다.
계획범위 비교는 '실제 섭취 탄수화물 에너지 / 실제 섭취 총에너지'로 구하는 식단 구성비 평가와 다르다.
단백질의 10-20% 에너지 범위도 내부 trace에 기록하되, 공개 단백질 target은 연령과 성별 RNI를 사용한다.

## 5. 실제 섭취량과 품질 계산

FoodNutrient.value는 기존 수집 코드에서 해당 상품의 1회 제공량으로 환산되어 저장된다.

```text
SERVING: 배율 = quantity
GRAM: 배율 = quantity / serving_amount (serving_unit == g)
MILLILITER: 배율 = quantity / serving_amount (serving_unit == ml)
실제 섭취량 = Σ(각 상품의 1회 제공량 성분 * 배율)
```

- g↔ml에는 밀도가 필요하므로 자동 환산하지 않는다.
- SERVING은 이미 제공량당 성분값이 있으므로 제공량의 질량이 없어도 계산할 수 있다. 이때 resolvedAmount.amount/unit은 null이다.
- 단위가 g/mg/µg 사이이면 명확한 질량 환산만 수행한다. 비타민 A는 RAE 표시를 요구하고 IU를 임의 환산하지 않는다.
- 확인된 0은 실제 0으로 합산한다. 음수, NaN, 무한대, 단위 불일치와 미확인 품질은 누락으로 처리한다.
- 해당 영양소가 상품 하나라도 누락되면 전체 actual/ratio를 null, status=UNKNOWN, quality=MISSING으로 반환한다. 알려진 일부 합을 전체 합처럼 표시하지 않는다.
- 전부 CONFIRMED이면 CONFIRMED, 전부 ESTIMATED이면 ESTIMATED, 두 품질이 섞이거나 MIXED가 있으면 MIXED다.
- 계산과 판정은 반올림 전 값으로 수행한다. 실제량과 목표량은 소수 2자리, 비율과 추천점수는 4자리로 마지막에 반올림한다. 따라서 표시값끼리 나눈 수와 ratio의 끝자리가 다를 수 있다.
- 가격은 제공량 배율에 비례한 섭취분 추정 비용이다. 원 단위 반올림 후 합산하며 실제 구매 결제액과는 다를 수 있다. 한 항목이라도 가격/배율이 없으면 totalPrice=null이다.

## 6. 상태 판정과 상한

ratio = 실제 섭취량 / 한 끼 target. percent가 아닌 배수다.
아래 ADEQUATE는 서비스 계획 목표를 충족한다는 뜻이며 건강상 안전이나 충분을 확정하지 않는다.

| 종류 | LOW | ADEQUATE | HIGH / UNKNOWN |
|---|---|---|---|
| 에너지 | target의 80% 미만 | 80-120% | 120% 초과 HIGH |
| 탄수화물 | 한 끼 계획범위 하한 미만 | 계획범위 내 | 상한 초과 HIGH |
| 단백질, 칼슘, 비타민 A와 C RNI | 한 끼 target 미만 | target 이상 | 적용 가능한 하루 UL 초과 시 HIGH |
| 비타민 D AI | 사용하지 않음 | 배분된 AI 이상 | AI 미만 UNKNOWN, 하루 UL 초과 HIGH |
| 기준 미적용 또는 성분 누락 | 사용하지 않음 | 사용하지 않음 | UNKNOWN |

에너지 80-120%는 논문의 정확예측 범위나 KDRI의 임상 경계가 아니라 **명시적인 서비스 피드백 정책**이다.
탄수화물의 HIGH도 계획범위 초과라는 의미이지 독성이나 상한섭취량 초과가 아니다.
단백질 RNI의 120%를 먹었다고 HIGH로 만들지 않는다. AI 미만만으로 부족을 판정하지 않는다.

| 연령 | 칼슘 남 mg/일 | 칼슘 여 mg/일 | 비타민 C mg/일 | 비타민 D µg/일 |
|---|---:|---:|---:|---:|
| 6-8 | 3000 | 2500 | 750 | 40 |
| 9-11 | 3000 | 2500 | 1100 | 60 |
| 12-14 | 3000 | 2500 | 1400 | 100 |
| 15-18 | 3000 | 2500 | 1600 | 100 |

upperLimit은 이 **하루 UL 원값**이다. 임의로 3등분해 한 끼 독성 상한을 만들지 않는다.
한 끼 기록만으로 하루 UL을 넘으면 HIGH지만, 넘지 않아도 다른 끼니와 보충제를 합치면 넘을 수 있다.
UI가 upperLimit을 한 끼 목표와 동일 분모로 해석하지 않도록 경고를 함께 읽어야 한다.
비타민 A의 레티놀형 상한은 내부 자료에 보존하되, DB에는 총 RAE만 있어 upperLimit=null로 반환한다.
단백질과 탄수화물의 upperLimit=null도 무제한 섭취가 괜찮다는 뜻이 아니다.

## 7. 설명 가능한 보완 식품 추천

현재 API에는 추가 섭취량 필드가 없으므로 후보 **1회 제공량**씩 개별 평가한다.
보완 대상은 평가 가능한 LOW 영양소만이며, AI 미만의 비타민 D나 기준 밖인 철분과 나트륨을 '결핍' 추천 근거로 쓰지 않는다.

```text
gap_i = target_i - actual_i
gain_i = min(candidate_i, gap_i) / target_i
score = 평균(gain_i)   # 해당 식사에서 LOW인 영양소들
```

서로 다른 g/mg 수치를 직접 더하지 않는다. 남은 목표량 이상은 추가 점수를 얻지 않는다.
동일 가중치, 상위 3개와 동점 foodId 순서는 서비스 정책이며 검증된 건강 점수가 아니다.

- 이미 먹은 foodId는 후보에서 제외한다.
- CU_ONLY는 기존 검색 기준처럼 품목보고번호가 있는 CU_PRODUCT만, ALL은 두 sourceType 모두 대상으로 한다.
- 모든 보완 항목과 에너지 성분을 알아야 점수를 계산한다.
- 추가 후 에너지 120% 범위나 평가 가능한 탄수화물 계획범위를 넘는 후보는 제외한다.
- 현재 합계가 알려진 칼슘, 비타민 C와 D에 대해 후보 값이 누락됐거나 추가 후 하루 UL을 넘으면 제외한다.
- 현재 합계가 누락된 영양소는 안전 여부를 평가할 수 없으므로 추천은 전반적인 안전 보증이 아니다.
- 추정 성분이 포함된 후보는 메시지와 quality에 표시한다.
- 후보가 없으면 빈 배열과 이유를 반환한다. 임의 식품이나 가상 성분값을 만들어 넣지 않는다.
- 철분과 나트륨 제한, 알레르기, 질환, 가격 최적화와 실제 재고는 이번 추천 범위 밖이다.

## 8. PDF 입력의 계산 예시

남아 14세, 165cm, 55kg, 하루 3끼, 저활동적 가정:

```text
H = 165 / 100 = 1.65m, PA = 1.13, G = 25
EER = 88.5 - 61.9*14 + 1.13*(26.7*55 + 903*1.65) + 25
    = 2589.9485 kcal/일
한 끼 kcal target = 2589.9485 / 3 = 863.316166... → 863.32
단백질 target = 60 / 3 = 20g
칼슘 target = 950 / 3 = 316.666... → 316.67mg
비타민 A target = 750 / 3 = 250µg RAE
비타민 C target = 90 / 3 = 30mg
비타민 D target = 10 / 3 = 3.333... → 3.33µg
탄수화물 target = 2589.9485 * 0.575 / 4 / 3 → 124.10g
```

416kcal를 섭취한 합성 예시에서는 ratio=416/863.316166...=0.4819, status=LOW다.
PDF의 833.33kcal는 형식 설명용 값이며 새 개인별 공식의 결과와 같을 필요가 없다.
DB 성분까지 실측 또는 공인 데이터로 채워야 actual을 실제 상품에 대한 값으로 설명할 수 있다.

## 9. 내부 추적과 발표 설명

build_targets(profile)는 (targets, trace)를 반환한다. trace에는 기준 버전, 연령군, PA, 성장에너지,
cm→m 변환값, 수치 대입식, EER, 끼니 수, 탄수화물 범위와 RNI, 단백질 에너지범위와 EAR가 있다.
이 내부 객체를 공개 응답에 덧붙이지 않아 JSON 계약을 보존한다.
발표에서는 '기준표 선택 → EER → 한 끼 배분 → 식품량 환산 → 누락 검사 → 비교 → 추천' 순으로 설명하면 된다.
공인 수치와 앱에서 선택한 배분, 판정과 추천 규칙을 구별하고, 한 끼 결과를 영양 결핍 진단으로 표현하지 않는다.

## 10. 기존 REST API에서 실행

기존 backend 환경에서 실행한다. 새 운영 의존성이나 새 라우터를 추가하지 않았다.

```powershell
cd backend
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --reload
```

Swagger `/docs`의 `POST /api/v1/meals/analyze`에서 아래 JSON을 보낸다.
foodId는 연결된 DB에 존재해야 한다. `cu:660`은 공모전 PDF의 예시 ID이며, 없으면 기존과 같이 404를 반환한다.

```json
{
  "mealType": "LUNCH",
  "eatenAt": "2026-09-16T12:30:00+09:00",
  "profile": {
    "sex": "MALE",
    "age": 14,
    "heightCm": 165,
    "weightKg": 55,
    "mealsPerDay": 3
  },
  "items": [
    {
      "foodId": "cu:660",
      "quantity": 1,
      "quantityUnit": "SERVING"
    }
  ],
  "recommendationScope": "CU_ONLY"
}
```

응답의 최상위 필드는 기존처럼 analysisId, mealType, items, totalPrice, nutrients, recommendations, warnings다.
실제 음식의 합산 에너지가 416kcal라고 가정하면, **전체 응답 중 `nutrients.kcal` 값만 발췌**한 결과는 다음과 같다.
성분 품질 ESTIMATED도 이 예시의 가정이며, 실제 값은 DB 품질에 따라 달라진다.

```json
{
  "actual": 416.0,
  "target": 863.32,
  "upperLimit": null,
  "unit": "kcal",
  "ratio": 0.4819,
  "status": "LOW",
  "quality": "ESTIMATED"
}
```

탄수화물과 비타민 D도 위와 동일한 7개 필드를 사용하며 각각 단위가 g, µg다.
analysisId를 제외한 계산 결과는 같은 기준 버전, 입력과 DB 성분이면 동일하다.
원본 PDF의 숫자는 입출력 형식 설명용이므로 새 개인별 계산값과 같을 필요가 없다.

## 11. DB 연결과 현재 한계

현재 수집 코드인 `scripts/import_data.py`와 `services/mfds.py`는 탄수화물과 비타민 D를 저장하지 않는다.
요청한 파일 범위를 지키기 위해 수집 코드, DB 모델과 스키마는 수정하지 않았다.
따라서 기존 DB에서 이 두 항목은 **목표량은 계산되지만 actual=null, ratio=null, status=UNKNOWN, quality=MISSING**일 수 있다.
이것은 0을 섭취했다는 뜻이 아니다.

DB 담당자가 기존 FoodNutrient 테이블에 다음 성분 행을 공급하면 별도 코드 변경 없이 계산한다.

| nutrient_key | unit | value의 기준 |
|---|---|---|
| carbohydrate | g | 해당 Food의 1회 제공량 기준 |
| vitaminD | µg | 해당 Food의 1회 제공량 기준 |

확인한 성분 데이터의 quality, source, source_ref도 함께 기록해야 한다.
실제 상품과 다른 표준식품을 연결하거나, 제공량 기준을 잘못 넣으면 엔진이 계산하더라도 정확한 상품 평가가 아니다.
프론트에서 표시할 영양소 키를 고정했다면 추가된 두 키의 화면 표시는 프론트 담당자의 후속 작업이다.
상품 구매 가격, 매장 재고, 식사 저장, 하루 종합 평가 API를 이번 변경으로 새로 구현하지는 않았다.

## 12. 검증 결과와 통합 상태

- 서윤님의 개발 기록 기준으로 별도 검증 환경의 영양 계산 테스트 52개를 통과했다.
- 저장소에는 EER 기준값, 연령과 성별 목표표, RNI와 AI 판정 및 API 응답을 확인하는 테스트를 추가했다.
- 저장소 테스트는 격리된 SQLite DB와 합성 식품 데이터로 수행한다. 실제 CU 상품 전체의 성분값을 검증한 것은 아니다.
- MySQL 운영 데이터와 실제 배포 화면은 병합 후 별도로 연결 검증해야 한다.
- 기존 임시 엔진 API 테스트는 실제 계산 결과를 확인하도록 갱신했다.
- FastAPI와 Starlette 테스트 클라이언트의 deprecation warning은 영양 계산 실패와 구분한다.
